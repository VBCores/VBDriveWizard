## 1. Общие сведения

### 1.1 Назначение

VBDriveWizard — настольное GUI-приложение для удобного взаимодействия пользователя с
электроприводами **VBDrive** (https://github.com/VBCores/VBDrive). Приложение закрывает
два основных сценария:

- **первичная настройка привода** — подключение, чтение/запись конфигурационных
  регистров, калибровка, сохранение/загрузка профилей настроек, обновление прошивки;
- **проверка работоспособности узлов привода** — мониторинг телеметрии в реальном
  времени, ручное и программное (траектории) управление приводом для диагностики.

### 1.2 Платформа и стек

| Параметр | Значение |
|---|---|
| ОС | Ubuntu 24.04 |
| Язык | C++ (стандарт C++17, см. [3.2](#32-используемые-qt-модули-и-сторонние-библиотеки)) |
| UI-фреймворк | Qt 6.4 (Widgets) |
| Система сборки | CMake (уже настроен в `CMakeLists.txt`) |
| Стиль кода | идиоматичный современный C++/Qt, эффективный по времени выполнения (без лишних копий, аллокаций и busy-wait там, где есть событийная альтернатива) |

## 2. Термины и сокращения

| Термин | Значение |
|---|---|
| Cyphal | Протокол обмена данными поверх CAN(FD), используемый VBDrive для CAN-подключения |
| DSDL | Data Structure Description Language — описание типов сообщений Cyphal, из которого генерируется C++-код |
| Node ID | Идентификатор узла (привода) на шине Cyphal/CAN |
| Heartbeat | Периодическое служебное сообщение узла Cyphal, сигнализирующее о его присутствии на шине |
| Регистр | Именованный параметр конфигурации/состояния привода, доступный на чтение и/или запись |
| FOC | Field-Oriented Control — векторное управление двигателем, используемое в приводе |
| Servo | Протокол управления приводом для типовых сценариев (положение/скорость/момент с ПИД-регулятором) |
| MIT | Протокол управления приводом (position/velocity/torque + Kp/Kd), ориентированный на робототехнику |
| SocketCAN | Подсистема ядра Linux для работы с CAN-шиной |
| OpenOCD | Open On-Chip Debugger — инструмент для прошивки микроконтроллеров через JTAG/SWD |

## 3. Архитектура и технологический стек

### 3.1 Слои приложения

Рекомендуемое разделение ответственности (реализация может использовать любые Qt-паттерны
— сигналы/слоты, `QObject`-сервисы в отдельных потоках — главное сохранить приведённую
ниже логическую структуру):

1. **UI-слой** — `MainWindow` поверх `mainwindow.ui`, диалоги (`PreferencesDialog`,
   диалог выбора модели для `RestoreRegBtn`, диалоги подтверждения/ошибок).
2. **Слой подключения (Connection layer)** — два независимых сервиса: Serial-сервис
   (`QSerialPort`) и CAN/Cyphal-сервис (libcxxcanard поверх SocketCAN). Отвечают за
   физическое соединение, обнаружение устройств, обмен сырыми кадрами/строками.
3. **Протокольный слой** — трансляция прикладных команд (чтение/запись регистра,
   отправка задающего сигнала) в конкретный протокол: ASCII key:value для Serial,
   Cyphal DSDL-сообщения для CAN.
4. **Модель данных привода** — на каждый обнаруженный привод: текущие значения
   регистров, `DeviceParamList` (снимок значений на момент первого подключения/выбора
   привода — см. [4.3.2](#432-механика-восстановления-параметров-restore)), состояние
   (Node ID, модель, статус связи).
5. **Воркеры реального времени** — независимые от UI потоки: скан heartbeat (CAN),
   опрос телеметрии/статуса (20 Гц), генераторы траекторий Servo (100 Гц) и MIT (1 кГц),
   прошивальщик (`QProcess` + OpenOCD). Подробности — [3.9](#39-потоковая-модель).
6. **Графики** — контроллер поверх QCustomPlot, подписанный на поток телеметрии
   выбранного сигнала (см. [4.4.3](#443-график)).

### 3.2 Используемые Qt-модули и сторонние библиотеки

| Модуль/библиотека | Назначение |
|---|---|
| `Qt::Widgets` | базовый UI |
| `Qt::SerialPort` | работа с Serial-подключением (по аналогии с `SerialPortService`/`SerialWorker` в RWIP_GUI) |
| `Qt::PrintSupport` | требуется QCustomPlot |
| `Qt::Network` | скачивание последнего релиза прошивки со страницы релизов GitHub VBDrive |
| `Qt::LinguistTools` | генерация `.qm` из `.ts` при сборке (уже подключено) |
| `QCustomPlot` (сторонняя, header+cpp) | отрисовка графика в реальном времени; вендорить в `third_party/qcustomplot`, как в RWIP_GUI |
| `libcxxcanard` (сторонняя) | C++-обёртка над `libcanard`+`o1heap` для работы с Cyphal; вендорить/подключать как `add_subdirectory`, как в примере `vbdrive-min` |
| Nunavut (`nnvg`) | генерация C-структур из DSDL на этапе сборки CMake (см. `cyphal_types.cmake` в `vbdrive-min`) |
| YAML-библиотека (например, `yaml-cpp`, как в `ConfigManager` RWIP_GUI) | чтение/запись файлов регистров и, при необходимости, пользовательских настроек |

CMake-проект должен быть дополнен подключением перечисленных модулей и вендоренных
зависимостей по аналогии с тем, как это сделано в `RWIP_GUI/CMakeLists.txt` (QCustomPlot,
SerialPort, PrintSupport) и `vbdrive-min/CMakeLists.txt` (libcxxcanard, генерация DSDL).

### 3.3 Взаимодействие по CAN (Cyphal)

Реализация CAN-транспорта должна повторять архитектуру примера `vbdrive-min`:

- **Транспортный уровень** — `LinuxCAN` из `libcxxcanard` поверх SocketCAN. Важно:
  `LinuxCAN` всегда открывает сокет в режиме **CAN FD** — физический CAN-адаптер и
  интерфейс должны поддерживать CAN FD, иначе подключение по CAN невозможно.
- **DSDL-типы** генерируются Nunavut из двух репозиториев данных: `public_regulated_data_types`
  (стандартные `uavcan.*` типы) и `voltbro_types` (типы привода `voltbro.foc.*`), как это
  настроено в `cyphal_types/cyphal_types.cmake` примера `vbdrive-min`.
- **Обнаружение узлов** — подписка на `uavcan.node.Heartbeat.1.0` (фиксированный порт
  `7509`); при получении heartbeat от нового Node ID — опрос его модели и Node ID (см.
  [4.1.4](#414-подключение-по-can)).
- **Чтение/запись регистров** — сервисы `uavcan.register.Access.1.0` (порт `384`) и
  `uavcan.register.List.1.0` (порт `385`). Чтение регистра выполняется запросом
  `Access.Request` с заполненным `name` и пустым `value` (tag `REGISTER_EMPTY_TAG`);
  привод в ответе возвращает текущее значение, ничего не меняя. Перечисление всех
  регистров привода — последовательные запросы `List.Request` с возрастающим `index` до
  получения пустого имени.
- **Телеметрия** — сообщение `voltbro.foc.state_simple.1.0` на фиксированном порту
  `3811` (broadcast от привода).
- **Команды**:
  - полная FOC-команда `voltbro.foc.command.1.0` — порт `2107 + NodeID`;
  - простой сетпоинт `voltbro.foc.specific_control.1.0` — порт `3407 + NodeID`.
- Реализация должна уметь работать одновременно с несколькими Node ID на шине
  (несколько подключённых приводов, см. [4.2](#42-devices-список-устройств)).

> Список регистров, их точные имена, типы и назначение нужно брать из актуального
> состояния репозитория VBDrive на момент реализации — пример `vbdrive-min` (22
> регистра вида `state.is_on`, `limit.current`, `angle.offset`, `node.id`, `foc.kp`…)
> и черновик [TZ_gui_short.md](TZ_gui_short.md) (упоминает `is_on`, `ang_off`,
> `servo_tr_form`, `servo_tr_vel`, `vbdrive_model` без точечной нотации) расходятся по
> именам. См. [10. Открытые вопросы](#10-открытые-вопросы-и-допущения).

### 3.4 Взаимодействие по Serial

Serial-подключение использует отдельный от Cyphal текстовый протокол «ключ:значение»
поверх `QSerialPort` (например, `is_on:1`, `node_id:?`). Реализация — по аналогии с
`SerialPortService`/`SerialWorker` из RWIP_GUI: обмен ведётся в отдельном потоке, UI не
блокируется на операциях чтения/записи порта.

`DataBaudLineEdit` и `NomBaudLineEdit` (вкладка CAN в [4.3](#43-configuration-конфигурация-привода))
задают **baudrate самой CAN-шины привода** (номинальный и data-сегмент CAN FD) — это
регистры привода, настраиваемые только через Serial-подключение, а не скорость самого
Serial-порта ПК.

### 3.5 График реального времени

Реализуется на **QCustomPlot** (та же библиотека, что и в RWIP_GUI, вендорится в
`third_party/qcustomplot`), включая построение осей, легенды, тёмной/светлой темы графика
и экспорт в PNG/CSV — по образцу `PlotController` из RWIP_GUI (`setupPlot`,
`applyTheme`, `appendSample`/`appendSamples`, `savePlots`, `saveCsv`, `setLiveMode`).

### 3.6 Хранение регистров (YAML)

Файлы регистров (`registers/*.yaml`) читаются/пишутся через YAML-библиотеку (рекомендуется
`yaml-cpp`, как в `ConfigManager` RWIP_GUI). Формат файла — плоский или вложенный список
`имя_регистра: значение`, покрывающий все регистры, редактируемые в группе
`ConfigGroupBox` (см. [4.3](#43-configuration-конфигурация-привода)).

### 3.7 Локализация

Используется штатный механизм Qt Linguist: `.ts`-файлы по языкам, компилируемые в `.qm`
на этапе сборки (`qt_add_translations`/`qt_create_translation`, как уже настроено для
`VBDriveWizard_en_US.ts`). Требуются три языка:

| Язык | Файл перевода |
|---|---|
| English | `VBDriveWizard_en_US.ts` (уже создан, пустой — требует заполнения) |
| Русский | `VBDriveWizard_ru_RU.ts` (создать) |
| 中文 (упрощённый) | `VBDriveWizard_zh_CN.ts` (создать) |

Переключение языка в `LanguageComboBox` должно применяться **в рантайме без
перезапуска приложения** (переустановка `QTranslator` + `retranslateUi`/ручной вызов
`retranslate()` на всех виджетах и контроллерах, включая график — по аналогии с
`TranslationController`/`LanguageManager` в RWIP_GUI).

### 3.8 Пользовательские настройки (Preferences)

Диалог, открываемый кнопкой **Preferences** (см. [4.4.4](#444-preferences)), хранит
настройки приложения (не связанные с конкретным приводом) — по аналогии с
`AppConfig`/`UiSettings` в RWIP_GUI: тема (`dark`/`light`), размер шрифта интерфейса,
параметры графика (размер шрифта на графике, толщина линии, временное окно, частота
перерисовки и т.п.). Настройки сохраняются между запусками (например, через `QSettings`
или тот же YAML-механизм, что и в RWIP_GUI `ConfigManager`). Выбор языка в диалог
**не входит** — он уже вынесен в `LanguageComboBox` главного окна.

### 3.9 Потоковая модель

| Поток/воркер | Частота / длительность | Назначение |
|---|---|---|
| CAN heartbeat-listener | работает 5 секунд после нажатия `CanConnectBtn` | слушает `uavcan.node.Heartbeat.1.0` от всех узлов на шине, инициирует опрос модели и Node ID для каждого нового узла |
| Опрос статуса/телеметрии | 20 Гц | обновляет `StatusGroupBox` и подаёт данные в график выбранного сигнала |
| Генератор траектории Servo | 100 Гц | формирует и отправляет задающий сигнал (User/Sin/Meander/Triangle) для конкретного привода, пока не остановлен |
| Генератор траектории MIT | 1 кГц | формирует и отправляет задающий сигнал (Step/остальные) для конкретного привода, пока не остановлен |
| Прошивальщик | на время заливки | запускает `OpenOCD` через `QProcess`, парсит прогресс из stdout (если доступно), обновляет `FlashProgressBar` |

Ключевое архитектурное требование (см. [TZ_gui_short.md, п. 30, 106–107, 119](TZ_gui_short.md)):
**потоки генераторов траектории привязаны к конкретному приводу (Node ID), а не к
текущему выбору в `DeviceList`.** Переключение выбранного привода в списке не
останавливает и не сбрасывает уже запущенные траектории других приводов — это нужно
для параллельной проверки нескольких приводов на шине CAN. Взаимодействие воркеров с
UI-потоком — через сигналы/слоты с `Qt::QueuedConnection` (или эквивалент), без прямого
доступа к виджетам из фоновых потоков.

## 4. Функциональные требования

### 4.1 Подключение

#### 4.1.1 Общее

- Приложение поддерживает подключение к приводу двумя способами: по **CAN** и по
  **Serial**. Выбор способа — переключатели `SerialRadioBtn` / `CanRadioBtn`.
- Список актуальных Serial-устройств отображается в `SerialCombo`, список CAN-интерфейсов
  — в `CanCombo`. Кнопки `SerialRefreshBtn` / `CanRefreshBtn` обновляют соответствующие
  списки.

#### 4.1.2 Состояния `ConnectionGroupBox`

- Пока приложение **не подключено** к приводу, все элементы управления приложения
  отключены (`enabled=false`), кроме: `SavePltCsvBtn`, `SavePltPngBtn`,
  `SignalComboBox`, `UnitsComboBox`, `LanguageComboBox`. После успешного подключения все
  элементы становятся активны, если для них не задано отдельное условие (см. ниже и
  [4.3](#43-configuration-конфигурация-привода)).
- Пока активно **Serial**-соединение: все элементы внутри `ConnectionGroupBox`, кроме
  `SerialConnectBtn`, отключены. `SerialConnectBtn` активен, текст меняется на
  `Disconnect`; повторное нажатие возвращает подпись `Connect` и разблокирует остальные
  элементы `ConnectionGroupBox`.
- Пока активно **CAN**-соединение: аналогично, но управляющий элемент — `CanConnectBtn`.
- При подключении по **CAN** поля `DataBaudLineEdit` и `NomBaudLineEdit` остаются
  `enabled=false` в любом случае — их можно менять только по Serial (см. [3.4](#34-взаимодействие-по-serial)).

#### 4.1.3 Подключение по Serial

1. По нажатию `SerialConnectBtn` открывается порт, выбранный в `SerialCombo`.
2. Сразу после открытия отправляется запрос регистра `vbdrive_model`.
3. Если получен ответ — устройство считается подключённым, UI переходит в состояние
   «подключено» (см. [4.1.2](#412-состояния-connectiongroupbox)), приводу задаётся
   регистр `is_on:1`.
4. Если ответа нет (таймаут) — показывается диалог с ошибкой подключения, приложение
   остаётся в состоянии «не подключено».

#### 4.1.4 Подключение по CAN

1. По нажатию `CanConnectBtn` на выбранном в `CanCombo` интерфейсе запускается
   heartbeat-listener (см. [3.9](#39-потоковая-модель)) на 5 секунд.
2. Для каждого Node ID, от которого пришёл heartbeat, выполняется опрос модели привода
   и Node ID; результат добавляется в `DeviceList` (см. [4.2](#42-devices-список-устройств)).
3. По истечении 5 секунд (или раньше, если реализация посчитает это уместным)
   соединение считается установленным, UI переходит в состояние «подключено», для
   **каждого** обнаруженного привода задаётся регистр `is_on:1`.
4. Если за 5 секунд не найдено ни одного привода — показывается диалог с ошибкой
   подключения.

#### 4.1.5 Отключение

При отключении (нажатие `Disconnect`) для всех подключённых приводов явно задаётся
регистр `is_on:0`, после чего интерфейс возвращается в состояние «не подключено».

#### 4.1.6 Внезапный обрыв связи

*(Раздел уточнён и расширен относительно черновика — детали см. также [5. Обработка ошибок](#5-обработка-ошибок-и-нештатных-ситуаций).)*

- **Serial**: потеря связи (порт исчез, устройство перестало отвечать) трактуется как
  обычное отключение — приложение переходит в состояние «не подключено» так же, как при
  нажатии `Disconnect` пользователем.
- **CAN, пропал не выбранный привод**: привод молча удаляется из `DeviceList`, без
  всплывающих сообщений.
- **CAN, пропал выбранный (активный) привод**: пользователю показывается модальное
  сообщение с двумя вариантами действия:
  - *подключить снова* — приложение ожидает возобновления heartbeat от этого же Node ID
    и восстанавливает работу с приводом без потери введённых, но ещё не отправленных
    изменений регистров;
  - *убрать соединение с приводом* — все несохранённые изменения параметров этого
    привода отменяются (как если бы для каждого изменённого регистра нажали Restore),
    привод удаляется из `DeviceList`.

### 4.2 DEVICES (список устройств)

- `DeviceList` отображает все приводы, подключённые к ПК в данный момент, двумя
  колонками: **Модель привода** и **Node ID**. Элементы группы `DevicesGroupBox`
  активны (`enabled=true`) только при подключении по CAN.
- При первом формировании списка активным (выбранным) считается элемент, обнаруженный
  первым.
- Пользователь может упорядочивать список по модели или по Node ID.
- Выбор нового элемента в списке переключает контекст работы: все последующие команды
  адресуются только выбранному приводу, чтение данных ведётся только с него.
- При выборе другого привода **команды, связанные с формированием траектории**
  (синус, меандр, треугольник, step и т.п.), не прерываются — соответствующий поток
  продолжает работать и отправлять команды приводу, для которого он был запущен (см.
  [3.9](#39-потоковая-модель)).
- При попытке переключиться на другой элемент списка, если у текущего привода есть
  несохранённые изменения регистров, показывается диалог с выбором **Да / Нет / Отмена**
  (сохранить изменения / не сохранять / отменить переключение).

### 4.3 CONFIGURATION (конфигурация привода)

#### 4.3.1 Общее

`ConfigGroupBox` отображает конфигурационные регистры привода на четырёх вкладках:

| Вкладка | Назначение |
|---|---|
| Basic | базовые параметры — ограничения работы привода и направление вращения |
| CAN | параметры шины CAN (включая baudrate, редактируемые только по Serial) |
| Advanced | расширенные параметры, не предназначенные для рядового пользователя |
| System | калибровка датчика, сохранение/загрузка файлов конфигурации, обновление прошивки |

#### 4.3.2 Механика восстановления параметров (Restore)

- При первом подключении к приводу (и при каждом последующем выборе привода в
  `DeviceList`) все его регистры считываются и сохраняются в `DeviceParamList` —
  «эталонный» снимок значений на момент выбора привода.
- Когда пользователь меняет значение поля так, что оно начинает отличаться от значения
  в `DeviceParamList`, рядом с полем появляется лейбл **Restore** (в финальном UI —
  иконка, см. [6.2](#62-restore-иконки)).
- Нажатие на Restore возвращает поле к значению из `DeviceParamList`, после чего лейбл
  скрывается.
- `ReadRegBtn` — читает с привода все регистры, отображаемые в `ConfigGroupBox`,
  **не обновляя** `DeviceParamList` (то есть Restore продолжит сравнивать с исходным
  снимком, а не со свежепрочитанными значениями).
- `WriteRegBtn` — записывает в привод все регистры, отредактированные пользователем.
  Видимые лейблы Restore **не скрываются** после записи — у пользователя должна
  сохраняться возможность в любой момент вернуть предыдущие значения, даже если новые
  уже отправлены в привод.
- `Set Origin` — читает текущее показание датчика положения и записывает его в регистр
  `ang_off`, тем самым делая текущее положение нулевым.

#### 4.3.3 Вкладка Basic

Параметры представлены чекбоксами. Невыбранный чекбокс означает отсутствие ограничения —
в соответствующий регистр записывается `NaN`.

#### 4.3.4 Вкладка CAN

Поля `DataBaudLineEdit`/`NomBaudLineEdit` активны только при Serial-подключении (см.
[4.1.2](#412-состояния-connectiongroupbox), [3.4](#34-взаимодействие-по-serial)).

#### 4.3.5 Вкладка Advanced

`EncoderTypeComboBox` содержит три пункта (`rotor`, `shaft`, `external`), но на момент
разработки привод поддерживает только `rotor` и `shaft`. Пункт `external` должен быть
скрыт в UI, но реализован так, чтобы его можно было включить одной правкой, когда
поддержка появится в прошивке.

#### 4.3.6 Вкладка System

- **Калибровка** (`CalibrateBtn`) — отправляет команду `CALIBRATE`. Кнопка доступна
  только при Serial-подключении (по CAN команда калибровки пока не реализована на
  стороне привода). На данный момент по отправке команды никакого ожидания ответа не
  требуется; в будущем протокол будет расширен последовательностью `CALIBRATE OK` →
  проценты выполнения → `CALIBRATE FINISH` — реализацию стоит закладывать так, чтобы
  это расширение протокола не потребовало переделки UI (например, `FlashProgressBar`-подобный
  индикатор прогресса калибровки уже сейчас предусмотреть в разметке скрытым/неактивным).
- **Файлы регистров** — в `registers/` должны существовать по умолчанию файлы
  `vbdrive_m4310r36.yaml` и `vbdrive_m4310r10.yaml`, заполненные значениями по
  умолчанию из репозитория VBDrive. На момент написания ТЗ содержимое обоих файлов
  должно быть одинаковым (сами модели пока не имеют различающихся дефолтов).
- `SaveRegBtn` — открывает диалог сохранения текущего состояния всех регистров привода
  в новый YAML-файл.
- `LoadRegBtn` — открывает диалог выбора существующего YAML-файла; после загрузки
  обновляются все поля регистров в UI, но `DeviceParamList` **не обновляется** —
  Restore-лейблы ведут себя как обычно (сравнение по-прежнему идёт с исходным снимком).
- `RestoreRegBtn` — открывает новый `QDialog` (нужно создать) с `QComboBox` выбора
  модели привода (`M4310R10` / `M4310R36`); по нажатию OK параметры загружаются из
  соответствующего файла (`vbdrive_m4310r10.yaml` / `vbdrive_m4310r36.yaml`).
- **Прошивка** — см. отдельный раздел [9](#9-обновление-прошивки-через-openocd).

### 4.4 REALTIME DATA (данные в реальном времени)

#### 4.4.1 Единицы измерения

`UnitsComboBox` переключает единицы измерения углов между градусами и радианами; выбор
влияет на всё приложение (отображение и ввод углов). Привод всегда работает во
внутренних единицах — радианах; приложение самостоятельно и прозрачно для пользователя
конвертирует значения при отправке параметров в привод, чтобы исключить некорректную
работу привода из-за единиц измерения.

#### 4.4.2 Язык интерфейса

`LanguageComboBox` переключает язык интерфейса между английским, русским и китайским
(см. [3.7](#37-локализация)). Весь текст приложения должен иметь перевод на все три
языка.

#### 4.4.3 График

Вместо статичного `PlotLabel` отображается график телеметрии в реальном времени
(QCustomPlot, см. [3.5](#35-график-реального-времени)):

- `SignalComboBox` выбирает, какой сигнал отображается. При переключении сигнала
  отрисовывается **только выбранный сигнал** — не должно быть фоновых чтений/отрисовок
  неотображаемых сигналов, чтобы не создавать лишнюю нагрузку на систему.
- Если у выбранного сигнала есть задающее (желаемое) значение — оно также отображается
  на графике вместе с фактическим.
- Кнопки **Pause**, **Save as CSV**, **Save as PNG** работают по аналогии с
  одноимёнными в RWIP_GUI и применяются к текущему выбранному сигналу.

#### 4.4.4 Preferences

Кнопка **Preferences** открывает диалог настроек приложения (см.
[3.8](#38-пользовательские-настройки-preferences)) — оформление, размеры шрифтов,
параметры графика и т.п., по аналогии с RWIP_GUI. Языка в этом диалоге нет — он уже
выведен в `LanguageComboBox` главного окна.

### 4.5 STATUS (статус привода)

`StatusGroupBox` отображает текущее состояние привода, обновляясь с частотой **20 Гц**.
Все лейблы должны иметь осмысленные названия (не дефолтные `label_N`). `FaultLabel`
отображает значения `Yes`/`No`.

### 4.6 STOP (аварийная остановка)

Нажатие `EmergStopPushButton` останавливает все приведённые в движение приводы,
отправляя каждому регистр `is_on:0`.

### 4.7 CONTROL (управление)

Группа `ControlGroupBox` задаёт желаемое состояние привода. Поддерживаются два
протокола управления — **Servo** (проще для новичков) и **MIT** (для сложного
управления роботами). Все элементы группы должны иметь осмысленные имена (не дефолтные).

#### 4.7.1 Вкладка SERVO

- **Control Type** — выбор типа задающего сигнала (Position / Velocity / Torque).
- **Transient Form** — тип переходного процесса; параметры пишутся в регистры
  `servo_tr_form` и `servo_tr_vel` по нажатию кнопки **Set**.
- **Feedback Gains** — коэффициенты регулятора для выбранного в Control Type типа
  управления:
  - `Position` — все элементы активны;
  - `Velocity` — активны только `Kp` и `Ki`;
  - `Torque` — ничего не активно, включая кнопку `Set`.

  По нажатию `Set` коэффициенты записываются в соответствующие регистры.
- **RefTrajectoryTabWidget** — вкладки по типу траектории: `User` (произвольное
  значение, задаётся вручную), `Sin`, `Meander`, `Triangle` (параметры формы сигнала).
  По нажатию **Start** в отдельном потоке (100 Гц, см. [3.9](#39-потоковая-модель))
  запускается расчёт и отправка траектории приводу. Если пользователь переключается с
  одной формы траектории на другую (например, с Sin на Triangle) во время работы —
  формирование должно переключиться на новую выбранную траекторию без остановки
  управления.
- При подключении по CAN смена выбранного в `DeviceList` привода **не останавливает**
  уже запущенную траекторию (см. [3.9](#39-потоковая-модель), [4.2](#42-devices-список-устройств)) — это
  нужно для одновременной проверки нескольких приводов на шине.
- Во время отработки траектории пользователь должен иметь возможность менять тип
  управления, форму переходного процесса и коэффициенты регулятора «на лету».
- Частота формирования траектории — **100 Гц**.

#### 4.7.2 Вкладка MIT

- **Trajectory** — выбор формы задающей траектории.
- `StepTargetsGroupBox` видим только при выборе траектории `Step`.
- `TrajectoryTargetsGroupBox` видим при выборе любой другой траектории.
- В `StepTargetsGroupBox` поля один в один соответствуют сообщению `mit_cmd` (Serial)
  либо `voltbro.foc.MITCommand.1.0` (Cyphal/CAN).
- В `Trajectory Targets` задаются амплитуда и частота сигнала. Радиокнопки
  `Position`/`Velocity`/`Torque` определяют, для какой величины формируется
  периодический сигнал (например, при выборе `Torque` синусоида формируется только для
  момента). Здесь же задаются коэффициенты `Kp` (position gain) и `Kd` (velocity gain).
- При выборе `Position` становится доступен чекбокс **+derivative** — вместе с заданным
  положением приводу дополнительно передаётся скорость, вычисленная как производная от
  траектории положения.
- Кнопка **Start** запускает отправку выбранного сигнала в отдельном потоке (1 кГц),
  который, как и в режиме Servo, продолжает работать независимо от переключения
  выбранного привода в `DeviceList`.
- Частота формирования траектории — **1 кГц**.

## 5. Обработка ошибок и нештатных ситуаций

| Ситуация | Ожидаемое поведение |
|---|---|
| Нет ответа на запрос `vbdrive_model` при подключении (Serial или CAN) | диалог с ошибкой подключения, приложение остаётся в состоянии «не подключено» (см. [4.1.3](#413-подключение-по-serial), [4.1.4](#414-подключение-по-can)) |
| Обрыв Serial-соединения во время работы | приложение переходит в состояние «не подключено», как при штатном Disconnect (см. [4.1.6](#416-внезапный-обрыв-связи)) |
| На CAN-шине пропал heartbeat непроверяемого/невыбранного привода | привод тихо убирается из `DeviceList` |
| На CAN-шине пропал heartbeat выбранного (активного) привода | модальное уведомление с выбором «подключить снова» / «убрать соединение с приводом» (см. [4.1.6](#416-внезапный-обрыв-связи)) |
| Таймаут запроса `uavcan.register.Access`/`List` | запрос считается неуспешным; поле регистра сохраняет предыдущее отображаемое значение, пользователю следует сообщить об ошибке чтения/записи конкретного регистра, не блокируя остальной UI |
| Попытка записи в `immutable`-регистр или регистр, отклонённый приводом (`Access.Response` с признаком отказа) | сообщить пользователю, какой регистр не удалось записать, значение в UI не считать применённым (Restore остаётся доступным) |
| Ошибка чтения/записи YAML-файла (`SaveRegBtn`/`LoadRegBtn`/`RestoreRegBtn`) | диалог с описанием ошибки (например, некорректный формат файла, нет прав на запись) |
| Ошибка прошивки (OpenOCD завершился с ошибкой) | сообщение об ошибке с (по возможности) текстом из stderr/stdout OpenOCD, `FlashProgressBar` сбрасывается |

> Поведение при временной потере связи с выбранным CAN-приводом в части траектории
> (приостановка отправки команд до переподключения) — принятое по умолчанию решение,
> вынесенное в [10. Открытые вопросы](#10-открытые-вопросы-и-допущения) как требующее
> подтверждения.

## 6. Требования к пользовательскому интерфейсу

### 6.1 Именование виджетов

Все виджеты, всё ещё носящие имена по умолчанию, присвоенные Qt Creator (`label_N`,
`doubleSpinBox_N`, `checkBox`, `horizontalSlider_N` и т.п.), должны быть переименованы в
осмысленные имена — по аналогии с уже корректно названными виджетами на вкладке Basic.
Это касается всех групп, включая `ConfigGroupBox` и `ControlGroupBox` (см.
[TZ_gui_short.md, п. 41, 99](TZ_gui_short.md)).

### 6.2 Restore-иконки

Лейблы Restore лишаются текста «Restore» и вместо него отображают иконку
`icons/restore.svg`; при наведении курсора иконка меняет цвет, показывая пользователю,
что элемент кликабелен.

### 6.3 Языковые флаги

В `LanguageComboBox` рядом с названием каждого языка отображается флаг страны, где этот
язык распространён, из уже подготовленных файлов `icons/flag_uk.png` (English),
`icons/flag_russia.png` (Русский), `icons/flag_china.png` (中文).

### 6.4 Тема оформления

Приложение поддерживает тёмную и светлую темы по аналогии с `ThemeManager` RWIP_GUI
(единое применение темы к `QApplication`, отдельным виджетам и графику). Фирменной
цветовой палитры Voltbro для этого проекта не задано — за основу берётся оформление
RWIP_GUI и уже подготовленные логотипы; окончательный выбор акцентных цветов и форм
элементов остаётся на усмотрение разработчика (см.
[10. Открытые вопросы](#10-открытые-вопросы-и-допущения)).

В `LogoLabel` отображается логотип компании-разработчика Voltbro, файл выбирается в
зависимости от активной темы: `icons/voltbro_logo_white.png` для тёмной темы,
`icons/voltbro_logo_dark.png` для светлой.

### 6.5 Дополнительные иконки (рекомендация)

В `icons/` пока нет иконок для части действий интерфейса. Рекомендуется (не является
жёстким требованием — см. [10](#10-открытые-вопросы-и-допущения)) добавить, например:
иконки Pause/Resume для графика, Save as CSV/Save as PNG, индикатор состояния связи
(подключено/не подключено/ошибка), иконку предупреждения для диалогов ошибок.

## 7. Нефункциональные требования

- **Производительность**: при переключении отображаемого сигнала в `SignalComboBox`
  должен отрисовываться только он — никаких фоновых чтений/отрисовок остальных
  сигналов. Частоты обновления статуса (20 Гц), траектории Servo (100 Гц) и MIT (1 кГц)
  должны выдерживаться стабильно и не деградировать при длительной работе.
- **Отзывчивость UI**: любые операции ввода-вывода (Serial, CAN, файлы, OpenOCD)
  выполняются вне главного потока событий Qt; главный поток не должен блокироваться.
- **Потокобезопасность**: обмен данными между воркерами реального времени и UI-потоком
  — через механизм сигналов/слотов Qt с очередями (`Qt::QueuedConnection`) либо
  эквивалентную потокобезопасную передачу данных; прямой доступ к виджетам из фоновых
  потоков запрещён.
- **Надёжность связи**: приложение должно корректно обрабатывать внезапный обрыв
  связи по Serial и CAN, не оставляя приложение в неконсистентном состоянии (см.
  [5. Обработка ошибок](#5-обработка-ошибок-и-нештатных-ситуаций)).
- **Совместимость**: Ubuntu 24.04, Qt 6.4; для CAN-подключения требуется CAN
  FD-совместимый адаптер и интерфейс SocketCAN.
- **Расширяемость**: скрытые/заготовленные, но пока не активные возможности (например,
  `EncoderType external`, будущий протокол пошаговой калибровки) должны включаться
  минимальными изменениями, без переработки уже написанного кода.
- **Идиоматичность и эффективность кода**: современный C++ (RAII, `unique_ptr`/владение
  через Qt parent-child, минимизация лишних копий и аллокаций в горячих путях — циклах
  генерации траектории и обработки телеметрии).

## 9. Обновление прошивки через OpenOCD

- Обновление прошивки доступно **только при Serial-подключении**.
- `CurFirmwareRevLabel` отображает текущую версию прошивки, прочитанную из
  соответствующего регистра.
- Выбор источника прошивки — радиокнопки:
  - `ChooseFirmwareFileRadioButton` — активирует кнопку `OpenHexPushButton`, по нажатию
    на которую открывается диалог выбора `.hex`-файла;
  - `DownloadFirmwareRadioButton` — при заливке будет скачана последняя версия прошивки
    из релизов репозитория VBDrive (через `Qt::Network`, GitHub Releases API/страница
    релизов `VBCores/VBDrive`).
- Кнопка `FlashPushButton`:
  - если выбран `ChooseFirmwareFileRadioButton` — заливается выбранный пользователем
    hex-файл;
  - если выбран `DownloadFirmwareRadioButton` — сначала скачивается последний релиз,
    затем заливается скачанный файл.
- Заливка выполняется через внешний процесс **OpenOCD** (`QProcess`); во время заливки
  `FlashProgressBar` отображает прогресс, если OpenOCD предоставляет такую информацию в
  своём выводе.
- Все файлы прошивок (скачанные и выбранные пользователем для однократной заливки,
  если применимо) хранятся в `firmwares/`.

> Точная конфигурация OpenOCD (interface/board/target cfg для микроконтроллера привода)
> в короткой версии ТЗ не задана — см. [10. Открытые вопросы](#10-открытые-вопросы-и-допущения).

## 10. Открытые вопросы и допущения

Ниже перечислены места, где при составлении настоящего ТЗ принято решение по умолчанию
либо оставлен открытый вопрос к автору/будущему разработчику. Рекомендуется явно
закрыть их до или в процессе реализации соответствующего раздела.

1. **Расхождение имён регистров.** Пример `vbdrive-min` использует точечную нотацию
   (`state.is_on`, `limit.current`, `angle.offset`, `node.id`, `foc.kp`, всего 22
   регистра), тогда как черновой TZ_gui_short.md упоминает регистры без точек
   (`is_on`, `ang_off`, `servo_tr_form`, `servo_tr_vel`, `vbdrive_model` и др.).
   Итоговый список регистров, их точные имена и типы нужно свести из актуального
   состояния репозитория VBDrive/прошивки на момент реализации соответствующей вкладки
   `ConfigGroupBox`, а не считать пример `vbdrive-min` или короткое ТЗ исчерпывающим
   источником истины.
   Ответ разработчика: правильные имена регистров даны в репозитории VBDrive

2. **Поведение траектории при временной потере связи с выбранным CAN-приводом.**
   Принято допущение: пока привод не переподключился (после выбора «подключить снова» в
   диалоге из [4.1.6](#416-внезапный-обрыв-связи)), формирование и отправку его
   траектории следует приостанавливать (отправка кадров в пропавшее устройство
   бессмысленна) и автоматически возобновлять после восстановления heartbeat. Это
   поведение не было явно описано в исходных требованиях и нуждается в подтверждении.
   Ответ разработчика: подтверждаю
3. **Конфигурация OpenOCD.** Не указано, какие interface/board/target cfg-файлы
   OpenOCD использовать для прошивки конкретного микроконтроллера привода — нужно
   взять из репозитория VBDrive (или прошивочных скриптов, если они там есть) на
   момент реализации раздела [9](#9-обновление-прошивки-через-openocd).
   Ответ разработчика: микроконтроллер STSPIN 32G431 (https://docs.vbcores.ru/docs/Hardware/vb-drive), программатор SWD (https://docs.vbcores.ru/docs/Hardware/stm-programmer), файл примера прошивки лежит в папке firmwares
4. **Состав дополнительных иконок** (см. [6.5](#65-дополнительные-иконки-рекомендация))
   — предложен ориентировочный список, финальный набор иконок и их вид остаются на
   усмотрение разработчика/дизайнера.
   Ответ разработчика: пока оставить текущие иконки
5. **Фирменная палитра Voltbro.** По ответу автора ТЗ — не важна/не задана; тема
   оформления берётся по аналогии с RWIP_GUI без привязки к конкретным HEX-цветам
   бренда.
   Ответ разработчика: да, палитру брать по аналогии из RWIP_GUI
6. **Формат хранения пользовательских Preferences** ([3.8](#38-пользовательские-настройки-preferences))
   — предложены `QSettings` или YAML-конфиг по аналогии с RWIP_GUI `ConfigManager`;
   конкретный механизм не был явно задан в исходных требованиях и выбирается
   разработчиком.
   Ответ разработчика: делать по аналогии с RWIP_GUI
